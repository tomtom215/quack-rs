# Security Policy

## Supported Versions

| Version        | Supported                               |
|----------------|-----------------------------------------|
| 0.20.x         | Yes                                     |
| 0.19.x         | Yes                                     |
| 0.18.x         | No (end-of-life)                        |
| 0.16.x         | No (end-of-life)                        |
| 0.3.x – 0.15.x | No (end-of-life); **do not use** (below) |

The two newest minor lines are supported. quack-rs is pre-1.0, so Cargo
treats each minor release as a new major line: a project that depends on
`quack-rs = "0.19"` never moves to 0.20 by itself. The previous line therefore
keeps receiving security fixes, as patch releases of that line, until the next
minor release ends its support. 0.18.x reached end-of-life with 0.20.0.

**Releases before 0.16.0 must not be used.** They carry the memory-safety
defects fixed in 0.16.0 (the "Security" part of its entry in `CHANGELOG.md`).
Checked against the published crates:

- `DuckStringView::from_bytes` (0.3.0 – 0.15.0) was a safe function that
  dereferenced a pointer read from its argument's bytes, so safe code could
  read arbitrary memory.
- `CopyGlobalInitInfo::get_file_path` (0.8.0 – 0.15.0) freed a string DuckDB
  still owned, corrupting the heap on every `COPY ... TO` through a quack-rs
  copy function.
- With the `duckdb-1-5` feature (0.4.0 – 0.15.0), nothing checked that the
  running DuckDB's C API function table had the layout the extension was
  compiled against; loaded into another DuckDB release, such a build could
  call the wrong functions (`double free or corruption`).

None of these versions has been yanked from crates.io; upgrade to a supported
line.

crates.io has no 0.1.x or 0.2.x: the first published version is 0.3.0. 0.17.x
does not appear either because it was never published: 0.17.0 was prepared
but not released, and its changes ship in 0.18.0 (see the 0.18.0 entry in
`CHANGELOG.md`). On crates.io, 0.18.0 follows 0.16.0.

## Reporting a Vulnerability

If you discover a security vulnerability in quack-rs, please report it responsibly.

**Do NOT open a public GitHub issue for security vulnerabilities.**

Instead, please use GitHub's
[private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability)
feature on this repository. Alternatively, email **tomf@tomtomtech.net**
with the subject line `[quack-rs security]`.

### What to include

- A description of the vulnerability
- Steps to reproduce (minimal test case preferred)
- The impact (e.g., memory safety, information disclosure, denial of service)
- The affected version(s)

### Response timeline

- **Acknowledgment**: Within 48 hours of report
- **Assessment**: Within 7 days
- **Fix**: Depends on severity; critical issues are prioritized

### Scope

This security policy covers:

- Memory safety issues in unsafe code (use-after-free, double-free, buffer overflow)
- Undefined behavior in FFI callbacks
- Panics that escape an FFI boundary (since Rust 1.81 an unwind out of an `extern "C"` function aborts the process instead of being undefined behaviour, which still takes down the host's DuckDB session)
- Information disclosure through uninitialized memory

This policy does **not** cover:

- Bugs in DuckDB itself (report those to [DuckDB](https://github.com/duckdb/duckdb))
- Bugs in `libduckdb-sys` bindings (report to [duckdb-rs](https://github.com/duckdb/duckdb-rs))
- Logic errors in extension code built with quack-rs (those are the extension author's responsibility)

## Security Design

quack-rs is designed with safety as a primary concern:

1. **`#![deny(unsafe_op_in_unsafe_fn)]`** in `src/lib.rs` and **`unsafe_op_in_unsafe_fn = "deny"`** in `Cargo.toml`: every unsafe operation needs an explicit `unsafe` block, even inside `unsafe fn`. Each `unsafe fn` documents its caller obligations under `# Safety`, and every `unsafe` block in library code carries a `// SAFETY:` comment, including a block inside an `unsafe fn` that only forwards that function's contract (the comment then names the clause it relies on). `clippy::undocumented_unsafe_blocks` is enabled and CI runs clippy with `-D warnings`, so an unannotated block fails CI. The convention is set out in the crate docs, `src/lib.rs`.
2. **No panics across FFI**: The entry points generated by `entry_point!` / `entry_point_v2!`, callbacks defined with the `*_callback!` macros (`src/callback.rs`), the closure-based builders and `FfiState<T>`'s callbacks run user code inside `catch_unwind` and report a panic as a SQL error. A raw `unsafe extern "C" fn` that an extension author passes to a builder is installed as written, with no guard; the author must use the matching macro or wrap the body in `callback::catch_ffi_panic`. The release profile therefore sets `panic = "unwind"`, **not** `abort`: under `panic = "abort"` a panic aborts the process before `catch_unwind` can run, which disables the crate's entire panic-containment mechanism. `validate_release_profile` rejects `abort` outright, and the generated scaffold never emits it.
3. **Double-free prevention**: `FfiState<T>::destroy_callback` clears each state's tag before dropping it.
4. **Boolean UB prevention**: `VectorReader::read_bool` reads as `u8 != 0`, never transmutes to `bool`.
5. **RAII for DuckDB handles**: `LogicalType` ensures `duckdb_destroy_logical_type` is always called.
6. **Credential protection**: `SecretEntry` redacts field values in `Debug`/`Display` output and zeroizes all sensitive data on `Drop` using `write_volatile`.
7. **TLS hardening**: `TlsConfigProvider` has no default minimum version — `min_tls_version` is a required method, so every provider states one — and `audit_tls_provider()` flags certificate-validation bypass (CWE-295) and deprecated protocol versions (CWE-327).
8. **Structured warnings**: `WarningCollector` provides thread-safe, CWE-annotated security warning collection for extensions.
